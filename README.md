# Частина 1 — відповіді

1. Аудіо-характеристики винесені в `audio_features`, бо це семантично схожі речі - зручніше працювати з ними вкупі і передавати одним шматком, ніж тягати з плоскої структури.

2. Виконавці - масив, бо це однорідні дані. Простіше перевірити, чи є артист серед авторів треку, ніж парсити рядок.

3. `$out` створює колекцію наново (перезаписує), `$merge` додає/зливає з уже існуючими даними.

# Частина 2 — відповіді

1. `$unwind` розгортає масив у окремі документи (наприклад, `artists: ["A","B"]` → два документи). Так зручніше групувати й рахувати по кожному елементу масиву.

2. `$stdDevPop` — стандартне відхилення для всієї сукупності (population), `$stdDevSamp` — для вибірки (sample, ділить на n-1). У нас по жанру беремо всі треки з бази, тому логічніше `$stdDevPop`.

# Частина 3 — відповіді

1. Поріг 1 фактично нічого не відсікає: у кожного артиста вже є хоча б 1 трек. Топ тоді легко забивають разові хіти (один трек з високою popularity). Якщо брати >50 треків — артистів менше, наступні кроки легші, а середнє стабільніше, бо не залежить від одного хіта.

2. Ні, не зміниться. У цьому датасеті жанри й так по ~1000 треків, тож і при 100, і при 50 проходять ті самі жанри.

# Частина 4 - відповіді

1. Було COLLSCAN по всій колекції, стало читання через індекс (IXSCAN) + FETCH лише потрібних документів. Examined = returned (354), час впав з 500+ мс до 1 мс.

2. Поля з explain():
   stage: FETCH
   totalDocsExamined: 354
   totalKeysExamined: 354
   nReturned: 354
   executionTimeMillis: 1

3. Ні, це не covered query. Індекс із завдання 1 тут навіть використовується (швидко, не COLLSCAN), але є FETCH і totalDocsExamined > 0 — Mongo все одно читає документи з колекції, бо find без projection повертає всі поля, а в індексі їх немає. Окремий індекс під цей запит я б не робив: поточний і так працює нормально, а ще один дорожче тримати на записах.
